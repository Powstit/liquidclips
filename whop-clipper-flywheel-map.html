02Stage by stage — what's real today

Create & fund Company whop Company escrows a reward pool directly on Whop's own dashboard. POST /v2/bounties exists on Whop's side; Liquid Clips has no create call anywhere in the codebase (confirmed by grep — zero write calls to Whop's bounty API).

Create the clip Clipper liquid clips The actual editing/export tool. This is the one stage nobody else provides — it's the real reason a clipper opens Liquid Clips at all.
Submit Clipper gap No write path. The clipper has to leave the app and submit on Whop's own bounty page. Our backend only has GET /whop/submissions/{id} — a status check on a submission that was already made elsewhere, not a way to make one.
Resolve Company (owner) whop Corrected 2026-08-14 per Daniel: not a community vote. The campaign owner reviews each submission by hand in Whop's own dashboard — a Pending / Approved / Flagged / Rejected board with Approve and Reject buttons (rejecting requires a reason, with an optional ban for bots). If the owner doesn't act in 48h and Whop's fraud-review AI flagged the clip as legit, it auto-approves. 03A second, smaller loop — Liquid-Clips-native campaigns

Not a Whop bounty at all — a parallel system.

Separate from anything Whop-hosted, sponsored_campaigns is Liquid Clips' own campaign table (10 rows today, several already audited and cleaned up this session). It has its own submission route —POST /submissions — but that route is currently hardcoded to one specific campaign ("Minecraft Story Clip Challenge"), with the code's own comment noting real Whop-campaign forwarding is still a future step, not built yet.

This is a genuinely different product: a company works directly with Liquid Clips (not Whop) to set up the campaign, and payout runs through Liquid Clips' own reward ledger rather than a Whop escrow pool. Worth knowing it exists so it doesn't get confused with the Whop-bounty loop above.

04Other Whop surfaces that touch this relationship

Not wired into either loop today — flagged because they overlap the same company↔clipper relationship and could plug into the flywheel without any new Whop permissions.

  • DM / messaging — Whop has a native DM-channel + message API. A company could message a clipper about their submission without leaving Whop; nothing prevents Liquid Clips from surfacing that thread read-only, same pattern as bounties.
  • Resolution Center (disputes) — if a clipper disputes a rejected submission, Whop already has a case/evidence flow for it. Currently invisible to Liquid Clips entirely.
  • Stats / Ad Reports — Whop's own aggregated metrics API (revenue, views, members by period) — a company could see campaign performance without either side building custom analytics.
  • Affiliate overrides — already deeply wired this session (the wallet-earnings fix) — but worth noting it's the same underlying override mechanism a company could extend to reward top clippers directly, not just referrers.

05The one gap your example pointed at

Submission is the seam. Everything before it (discover, create) and everything after it (resolve, payout, see earnings) already has a real Whop-API-backed path either fully or partially wired into Liquid Clips. Submission is the one stage where the clipper is handed off entirely — no API call, no in-app tracking of the act itself, just a link out.

That's not a new-functionality call — it's just the most visible place where "the app knows everything about this campaign right up until the moment that matters" is true today.

06What's actually leverageable at Resolve (2026-08-14 update)

Daniel's correction — he personally reviews clips in "the clipping reward backend" for a campaign he ran — checked against the API, not just the marketing docs.

Dead end, confirmed twice: there is no public endpoint for the Approve/Reject click itself. It's not in the stable bounties API (four endpoints total: Workforce Bounty, List Bounties, Create Bounty, Retrieve Bounty — no submission-review call among them). The beta bounty_submissions category exists but only exposes POST /bounty_submissions/{id}/submit — worker-side, and explicitly restricted to "the worker who started the attempt" (account API keys can't even call it). Whop's own help docs confirm the Approve/Reject/48h-auto-approve flow is dashboard-only. This means the owner will always leave Liquid Clips to do the actual review — that part can't be brought in-app without Whop shipping a new endpoint.

What we can leverage without any new Whop permission: GET /bounty_submissions is a list/read call under bounty:basic:read — a scope we already have — and per Whop's own docs it returns, for a user token, "the submissions they authored plus those on bounties they posted." That's exactly the Pending / Approved / Flagged / Rejected state (plus denial reason) the owner is producing by hand on Whop's side. Polling this and mirroring it into the clipper's Liquid Clips submission status — instead of the clipper having to tab back to Whop to check — closes the loop on our side of the seam even though the click stays on theirs. Same read-mirror pattern already proven this session for affiliate earnings.
